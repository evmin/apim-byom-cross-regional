# Foundry portal access via jumpbox SOCKS tunnel

The agent Foundry account has `publicNetworkAccess=Disabled`. The portal at `ai.azure.com` is public, but the browser-side JavaScript calls `<account>.services.ai.azure.com` — which only resolves to a reachable IP from **inside** the agent VNet (private DNS → private endpoint).

Routing your browser through the jumpbox VM with SOCKS5-over-SSH-over-Bastion makes the portal work end-to-end without changing system network settings.

## Prerequisites

- `az login` against the right subscription and tenant.
- `azd env select <env-name>` — the env that holds the deployed jumpbox values.
- A local SSH private key matching `JUMPBOX_SSH_PUBLIC_KEY` (default `~/.ssh/mreg-jumpbox`).
- Bastion is **Standard SKU with tunneling enabled** (this is what the IaC deploys). The VM admin user is `azureuser`, key-only SSH.

## One time — capture the targets

```bash
eval "$(azd env get-values | grep -E '^(jumpboxBastionName|jumpboxBastionResourceGroup|jumpboxVmId)=')"
```

Or set them explicitly from the `azd` outputs:

```bash
SUB=$(az account show --query id -o tsv)
RG="$jumpboxBastionResourceGroup"
BASTION="$jumpboxBastionName"
VM_ID="$jumpboxVmId"
```

## Step 1 — open the Bastion → port-22 tunnel (Terminal A, keep running)

```bash
az network bastion tunnel \
  --resource-group "$jumpboxBastionResourceGroup" \
  --name           "$jumpboxBastionName" \
  --target-resource-id "$jumpboxVmId" \
  --resource-port 22 --port 2222
```

Expect `Opening tunnel on port: 2222` then `Tunnel is ready`. Leave it open.

## Step 2 — open the SOCKS5 proxy (Terminal B, keep running)

```bash
ssh -N -D 1080 -p 2222 \
    -o StrictHostKeyChecking=accept-new \
    -i ~/.ssh/mreg-jumpbox \
    azureuser@127.0.0.1
```

- `-N` — no remote shell, port forwarding only.
- `-D 1080` — dynamic SOCKS5 proxy on `localhost:1080`.

No output on success. Leave it open.

## Step 3 — point your browser at `socks5://127.0.0.1:1080`

### Option A: Firefox (recommended — per-browser proxy, no system impact)

`Settings` → `Network Settings` → `Manual proxy configuration`:

| Field | Value |
|---|---|
| SOCKS Host | `127.0.0.1` |
| Port | `1080` |
| Protocol | `SOCKS v5` |
| ☑ Proxy DNS when using SOCKS v5 | **Required** |

The DNS checkbox is the critical bit — it makes Firefox resolve hostnames through the VM (which uses the VNet-linked private DNS zones) instead of locally.

Navigate to `https://ai.azure.com`, sign in, open your project. The "Private network access required" screen is gone.

### Option B: Chrome / Edge (isolated profile, single command)

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --user-data-dir=/tmp/foundry-portal-profile \
  --proxy-server="socks5://127.0.0.1:1080" \
  --host-resolver-rules="MAP * ~NOTFOUND , EXCLUDE 127.0.0.1" \
  https://ai.azure.com
```

For Edge, replace the binary path with `/Applications/Microsoft\ Edge.app/Contents/MacOS/Microsoft\ Edge`.

`--host-resolver-rules` forces all DNS through the SOCKS proxy. Chrome's default is to resolve locally even with SOCKS5.

## Verify the tunnel is doing what you think

From your laptop, over the SOCKS proxy:

```bash
PROJECT_FQDN=$(azd env get-value weFoundryProjectEndpoint | sed -E 's|^https?://([^/]+).*|\1|')

# Routing check — expect HTTP/2 401 (auth required, but the connection landed).
curl -x socks5h://127.0.0.1:1080 -sI "https://$PROJECT_FQDN/" | head -1

# DNS check — expect an RFC1918 address, not a public one.
curl -x socks5h://127.0.0.1:1080 -s "https://$PROJECT_FQDN/" -o /dev/null -w '%{remote_ip}\n'
```

`socks5h://` (not `socks5://`) is the curl idiom that delegates DNS to the proxy — same semantics as Firefox's "Proxy DNS" checkbox.

## Teardown

Ctrl-C both terminals. Reset Firefox proxy to `No proxy`, or close the Chrome isolated profile.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `Permission denied (publickey)` on Step 2 | Wrong private-key path, or wrong file permissions (`chmod 600 ~/.ssh/mreg-jumpbox`). |
| Portal still shows "private network access required" | Firefox "Proxy DNS" is off. The browser resolved the FQDN locally to a public IP. |
| Tunnel opens but `ssh` hangs | Step 1's `az network bastion tunnel` didn't reach `Tunnel is ready` yet. Wait for the line. |
| `az network bastion tunnel` fails with `not supported on sku` | Bastion is on `Basic`. The IaC deploys `Standard` with `enableTunneling=true`; if your env was regenerated by hand, fix the SKU. |
| Portal pages load slowly | Expected. Every request hairpins laptop → Bastion → VM → Azure backbone. |

## Why this works

The VM lives in the agent VNet, which is linked to the private DNS zones for `privatelink.services.ai.azure.com`, `privatelink.cognitiveservices.azure.com`, and the rest. When the browser asks the SOCKS5 proxy to resolve `<account>.services.ai.azure.com`, the VM's resolver answers with the private endpoint's IP. The SOCKS proxy then opens a TCP connection from inside the VNet to that PE, and the PE accepts the call — because `publicNetworkAccess=Disabled` allows only PE traffic. From the portal's perspective, your browser is a tenant of the agent VNet.
